本包提供本轮完整数值设计目标、可复现的生成器、历史资料和数学校验结果。<b>它不是游戏工程导出包，也不是已部署补丁。</b> JSON 中的 <code>Status</code>、<code>status</code>、<code>source_status</code>、<code>SourceURL</code> 与版本字段必须一起保留，不能只导入数值后将设计目标标成已实现。

## 一、先按用途选择权威表

| 文件与表 | 用途与优先级 |
| --- | --- |
| <code>core_tables.json → GlobalRules</code> | 人物单 DEF、怪物双防、等级/槽位/减伤等公共规则。本轮统一规则优先于历史页中的旧物法防人物字段。 |
| <code>core_tables.json → Character999</code> | 本轮 1—999 级完整人物设计曲线。已知锚点继承既有方案，中间行是本轮明确插值生成，不能冒充工程逐级导出。 |
| <code>core_tables.json → MonsterDesign75</code> | 八岛 75 条怪物的新设计目标，包括生命、攻击、双防、移动、攻击间隔下限和攻击距离应用规则。按 <code>MonsterId</code> 关联，保留现有模型、AI、技能和动作。 |
| <code>core_tables.json → MonsterLegacy75</code> | 历史实现快照，用于比较与迁移核对；不能与新怪物表叠乘，也不能与 <code>MonsterDesign75</code> 同时应用。 |
| <code>core_tables.json → CorePetReference</code> | <b>怪物推进平衡唯一的普通宠物参考入口。</b> 共 23 行：第一岛 2 只，其余七岛各 3 只。 |
| <code>core_tables.json → WeaponReferences</code>、<code>weapon_reference.json</code> | 八岛平衡选用的具体武器样板及触发频率。后者是 <code>build_core.py</code> 的冻结输入，前者是核心输出中的同份记录。 |
| <code>core_tables.json → IslandReferences / CombatScenarios225 / CombatSensitivity288</code> | 配装和完整周期输出模型的结果与敏感性分析。它们是设计比较结果，不是角色必须达到的门槛，也不是实机通关保证。 |

| <code>companion_tables.json → PetReferenceTeams</code> | <b>额外培养测试模板</b>，不作为本轮推进怪物生命的输入。字段名“常规参考”是旧模板标签，其用途由 <code>ScenarioRole</code> 与 <code>UseForProgressionMonsterCalibration=false</code> 明确限定。 |
| <code>economy_tables.json → tables</code> | 金币/经验覆盖、奖励额度、掉落、生产、修炼、道具、实体塔、通天塔、飞行、商品与 PVP 隔离测试规格。涉及替换的字段必须按下文覆盖规则处理。 |
| <code>arena_tables.json → tables</code> | <code>QC_Arena_Design_V3_Candidate</code> 新竞技规则集、100 队/300 槽及奖励。不能覆盖旧 T2 历史、现有排行或旧规则集存档。 |
| <code>budget_reference.py</code> | <code>QC_BUDGET_V2</code> 精确数值裁剪与事件预算参考内核。它定义实际效果如何随预算裁剪；工程仍须提供真实事件参数与适配。 |
| <code>sources/</code>、<code>audit_source/</code> | 本轮读取的 Notion 原文与 Stage3 技能审计依据。用于追溯历史、资产身份和不确定性；不是新的执行配置。 |
| 各 <code>*_validation.json</code>、各模块检查表、<code>core_cross_review.json</code> | 生成或审查时的验证记录，不是游戏配置。修改输入后，旧通过记录不能自动沿用。 |

本包冻结 JSON 是本轮交付的实施目标。修改设计时，应同步修改对应生成器参数、版本与结果，再重新生成和核对。不要单独改 JSON 后重跑脚本，误以为手改值会被保留。

### 武器原型的统一解锁接口

制造、直购和宝箱发放共用同一 <code>PrototypeUnlock</code> 资格：按物品对应的原型 ID 查询 <code>gear_tables.json → tables.weapon_catalog</code> 的 <code>prototype_unlock_key</code> 与 <code>prototype_unlock_rule</code>，并与配方中的同名条件保持一致。R 类要求本岛解锁；C 类要求本人本岛普通 BOSS 首通并完成该原型图样任务；M 类要求完成该原型对应的免费机制练习。具体原型按目录条目执行，金品质还须同时满足本人本岛挑战首通。配方材料齐全、金币足够或达到 <code>min_level</code> 都不能代替这项解锁校验，任何取得路径不得绕过；此接口不新增收费或任务奖励。

### 推进、高培养与额外模板的区别

<code>build_core.py</code> 的推进档使用紫装强化 5、星铸 0、C01 一阶炮台、无神宠，并按 <code>CorePetReference</code> 引用普通宠物。具体装备预算、词条与修炼见脚本和输出，不把“紫装”标签当作足够复现的全部条件。

<code>CorePetReference</code> 对每个候选物种假定取得时的人物等级，使用其后合法人物击杀经验的 10% 计算该宠经验上界，并受品质/星级上限和参考培养投入限制。<b>怪物出现时点不保证当场获得化石、孵化成功领取或已经具备目标品质。</b> 该表是清楚列出条件的测试阵容，不是掉落保底承诺。

每只在场宠独享主人合法击杀经验的 10%，三只之间不分摊。除既有品质/星级、资源支付与占用状态外，不添加“宠物等级不得超过主人”或按岛锁等级的新门槛。

核心高培养档的宠物攻击取以下两者较大值：

1. <code>PetReferenceTeams</code> 中本岛高培养模板的攻击总和。
2. <code>CorePetReference</code> 中本岛推进队的攻击总和。

二者不相加。第二岛高模板 673 低于推进队 1,036，因此核心高档采用 1,036。该选择允许高培养玩家继续使用更强的合法阵容。中间人物等级使用脚本明示的队伍预算插值，不代表导出了这些等级下的真实宠物阵容。

普通、挑战、极限 BOSS 的 60/90/120 秒目标针对<b>推进测试档的满命中完整周期模型</b>。高培养、迟取得宠物、资源不足、原生攻击空窗、走位、机关、倒地和多人协同都会改变实际耗时。

## 二、金币和经验必须替换旧奖励

经济表内的 <code>旧怪物掉落</code> 共 671 行，是历史奖励记录；<code>金币收益</code> 是旧掉金尺度的分析，不能继续充当新版经济总收入。

新版加载按以下顺序处理：

1. 以 <code>MonsterId</code> 读取历史掉落中仍然保留的材料、装备、票券等规则。
2. <b>金币奖励读取 </b><b><code>逐怪金币覆盖</code></b><b> 的 75 条 </b><b><code>final_gold</code></b><b>。</b> 替换同怪旧金币奖励，不在旧金币之外再发一份，也不再重复乘 <code>金币V2覆盖.gold_multiplier</code>。
3. <b>怪物经验读取 </b><b><code>逐怪经验覆盖</code></b><b> 的 75 条 </b><b><code>xp</code></b><b>。</b> 替换旧怪物经验；<code>角色经验投放V2</code> 给出其八岛基准、日上限与路线假设。秘境读取自身对应经验规则，不把主岛经验再次相加。
4. 金币倍率不用于材料数量、化石、保底进度、讨伐令、抽奖券或经验。主线、宝箱等奖励依其单独的新配置处理。
5. 先判断奖励资格、岛屿/难度/成员身份及共享日周额度，再生成唯一奖励事务。不能把同一次击杀在“旧掉落模块”和“新数值模块”分别结算。

小数经验按既定整数余额加百万分之一经验余量累计，不应每击向下舍弃小数。读取与保存应使用确定性定点口径，不以二进制浮点累计经济账本。

<code>成长资源闭环</code> 的时间是基于指定刷取构成与完整有效收益的设计结果，不代表所有玩家的实际日历毕业时间。原有金币/经验领取和新覆盖数据只允许有一个有效规则版本。

## 三、战斗路由与数值尺度

### 单 DEF 与双防

- 玩家仅有一个 <code>DEF</code>。怪物对玩家的所有合法攻击均读取它，不按怪物动画、投射物父类或技能表现判断物理/法术。
- 怪物有 <code>DEF</code> 与 <code>MDEF</code>。玩家武器和神宠读取显式设计的伤害类型，再选择怪物对应防御。
- <b>45 种普通宠物的 </b><b><code>DamageType=Physical</code></b><b> 是本轮新增的玩家所属宠物攻击规则。</b> 同一原生怪物在未驯服状态攻击玩家时，仍走玩家统一 DEF。这不构成“已经确认这些野怪的技能均为物理伤害”的审计结论。
- 维修球机基础 ATK 为 0，不通过通用伤害归一化给它创造攻击。未开放出战物种不因表格齐全自动变为可获得/可出战。
- 30 款悬浮炮台按自己的 Magical 路由结算；不重复继承一次主人武器伤害公式，也不默认继承主人暴击、暴伤、穿透或普攻触发。

防御使用承伤方固定尺度：人物 <code>K=0.4×本级裸装B0</code>，怪物 <code>K=0.4×生成参考等级B0</code>。归一化 <code>scale=K/400</code>，与 <code>DR=min(0.70, DEF/(K+DEF))</code> 等价。怪物不按攻击者当前装备、宠物数量或即时战力改变 K。

<code>MonsterDesign75</code> 的时间参数是明确的设计下限。实际攻击周期取本表下限与原生完整动作周期的较大者，不截断动画、多段攻击或 DOT；射程字段需由原生参数接受，不重建技能形状。原生技能冷却继续保留。

### 技能预算只计算一次

主人实际攻击 A 已包含合法装备、词条、修炼、装备神宠本体等贡献。神宠主动和炮台读取 A 后，不能再把这些来源乘一次。神宠与炮台的多段、多目标、DOT 和反击共享各自整次行动预算；失效份额依表丢弃，不挪给幸存目标。

同一稳定来源、行动、伤害包、目标须去重。追加伤害不伪造新的普攻事件；反击不能递归触发反击。冷却、聚能待发和倒地恢复时间不能被换装、重连或重新召唤重置。

普通宠物 <code>DesignCoefficientPerSecond=1</code> 是模型测试基准，<b>不是原生技能每秒固定攻击一次的已测事实</b>。需从完整原生周期测得输出，再按目标决定 <code>DamageScale</code>；实际周期伤害为 0 或没有测量时，禁止除以零或填写伪造校准系数。

<code>Weak800PetMinimumCoefficient</code> 表示最弱满级非零攻击宠物满足对应四人生命一击所需的最小原生有效系数。保留前六岛回刷一击目标，但仍需用真实原生首段验证，不以面板攻击和理论预算直接宣称每个技能已通过。

## 四、精确整数、定点与显示值

<code>1极=10^48</code>，远超 IEEE 754 双精度整数连续精确范围。<b>绝对值超过 </b><b><code>2^53−1</code></b><b> 的整数、需要保留小数的高数量级属性，以及货币/经验余量，不能先转成 JavaScript Number、C++ double 或 Lua 普通浮点再声称精确。</b> 小于该阈值也不意味着十进制小数可被二进制浮点精确表示。

字段处理规则：

| 字段形态 | 正确处理 |
| --- | --- |
| <code>*Exact</code>、<code>*_exact</code>、<code>MultiplierHundredthsExact</code> | 保留十进制字符串，读入任意精度整数、Decimal 或明确分母的定点数。不能先 <code>float()</code> 再转回字符串。 |
| <code>MultiplierApprox</code>、DPS/TTK 浮点展示、无精确保证的汇总列 | 用于展示和设计比较。不能作为精确属性存档或支付账本的权威来源。 |
| 装备锚点 <code>hp_fixed/attack_fixed/defense_fixed</code> | 表示显示整数；相应 <code>*_exact</code> 是六位定点锚点。最终生成仍以装备公式和指定舍入规则为准，不能把整数显示列当完整真实属性。 |
| 比例、权重与经验小数 | 从 JSON 十进制文本直接解析为 Decimal/定点。概率按明确总权重或分数抽取，显示四舍五入值不反写真实权重。 |
| 状态、ID、版本 | 按原字符串保留。不要把策划 <code>DesignKey</code> 自动当作已存在的工程资产 ID。 |

Python 读取示例：

```py
from decimal import Decimal
import json
from pathlib import Path

tables = json.loads(
    Path('core_tables.json').read_text(encoding='utf-8'),
    parse_float=Decimal,
)
hp = int(tables['Character999'][-1]['BaseHPExact'])
```

<code>budget_reference.py</code> 只接受 Python 任意精度 <code>int</code> 或 <code>Fraction</code>，主动拒绝 float。引擎原生生命/伤害仍可能经过 float 通道，需要单独定义可接受相对误差、权威逻辑值与实际读回值；本包不证明原生引擎可以对京级、极级生命逐个位精确扣除。

价格列为 0 时也要读 <code>price_status</code>、<code>status</code> 或 <code>shop</code>：有些记录表示“沿用既有 SKU”或“此处不配置该币种”，不能自动解释为免费售卖。未安装、未开放、待映射不是数值 0 的同义词。

## 五、版本、奖励与模式隔离

普通宠物新 800 行使用 <code>QC_Pet_Design_V3</code>。已有锚点与满级冻结基础保留，但没有取得工程 V2 的全部中间整数行，不能宣称逐行相同。旧 V2/T1/T2 快照及版本化还原逻辑应继续保留，不能直接用新配方解码旧阵容。

竞技新表使用 <code>QC_Arena_Design_V3_Candidate</code>，它是 100 队新的确定性设计候选。面板标定值单调只说明该标定指标排序，不证明不同原生 AI 的实战胜率/难度严格单调。竞技每项生命、攻击、防御的 1% 映射及小数应保持；不得向上强制钳成 1。

1001—1004 公平模式与 1005 PVE 分开读取规则。新 PVE 装备、神宠、炮台成长不会因玩家持有就自动进入公平 PVP 或标准宠物积分赛。经济文件中的 PVP 表是本轮隔离测试基准，不是旧运行配置的已验证导出。

炮台三池自然奖励与各档里程碑奖励属于不同权益：一抽只扣一券、发一个自然包，再各发一次本次到点的档位奖励。来源、版本、档位与保障目标分别计数。重复请求只返回原事务结果，不能重复扣发，也不能把多个同时到点奖励错误覆盖成一个。

首期 <code>PoolVersion=QC_HT_FIRST_V1_20261031</code>，点券14条、钻石13条、任务13条，跨池去重15型号。三池共用C01—06/B01—04/A01—02，点券和钻石用S02，任务用S01，仅点券有SS01。<code>NaturalProbabilityNumerator/Denominator</code> 是最终自然概率的权威分数；<code>NaturalProbabilityApprox</code> 只显示。钻石C单款为精确7/75。<code>AllowedGuaranteeTargetIds</code> 是同池同版本同档的完整可选列表，不能把全30款目录作为保障目标。这个版本键是冻结设计ID，不是已经上线奖池的证明。

## 六、如何重现本包

生成器使用 Python 标准库。把整个 <code>qc_design</code> 目录保留在一起，包括 <code>sources/</code>、<code>audit_source/</code> 与 <code>weapon_reference.json</code>，在目录内依次执行：

```bash
python3 build_companions.py
python3 build_gear.py
python3 build_economy.py
python3 build_arena.py
python3 build_core.py
python3 budget_reference.py
```

依赖关系与输出：

| 脚本 | 主要输入 | 主要输出 |
| --- | --- | --- |
| <code>build_companions.py</code> | 宠物冻结基础的源页及脚本内本轮参数 | <code>companion_tables.json</code>、<code>companions.md</code> |
| <code>build_gear.py</code> | 八岛装备源页及脚本内本轮参数 | <code>gear_tables.json</code> |
| <code>build_economy.py</code> | 生产、掉落、修炼、商品等源页 | <code>economy_tables.json</code>、<code>economy_validation.json</code> |
| <code>build_arena.py</code> | <code>companion_tables.json</code> | <code>arena_tables.json</code>、<code>arena_validation.json</code> |
| <code>build_core.py</code> | <code>companion_tables.json</code>、<code>weapon_reference.json</code>、怪物源页、Stage3 CSV | <code>core_tables.json</code>、<code>core_validation.json</code> |
| <code>budget_reference.py</code> | 内核自带的数学边界与事件用例 | <code>budget_validation.json</code> |

<code>weapon_reference.json</code> 是本次集成选定的八岛武器样板，现有生成器不会自动从所有武器中重新选择它。若更换样板或修改武器动作，应同步核对其类型、周期、主目标有效触发数、暴击部分与 DOT 部分，再生成核心结果。

脚本只重新生成本地表和检查记录，不连接游戏、不修改 Notion、不扣游戏资源、不上架商品。<code>core_review.md</code>、<code>core_cross_review.json</code> 及人工解释文档不会因为重跑生成器就自动完成新一轮审查。

退出码为 0 不足以认定所有检查通过：部分脚本输出失败列表而不主动抛异常。应读取各检查表的 <code>Passed</code>、<code>passed</code>、<code>pass</code> 与 <code>checks_failed</code>，处理失败后再打包。当前记录证明的是本次输入状态；改参数后应检查对应依赖结果，不能只沿用旧验证文件。

## 七、预算参考内核如何接入

<code>budget_reference.py</code> 提供 <code>Source</code>、<code>resolve()</code>、<code>score()</code> 和 <code>EventLedger</code>：

1. 工程适配层先把合法模式下实际启用、已去重的能力整理为稳定 <code>source_id</code>。同一神宠本体攻击不能同时作为人物 A 与额外独立攻击来源再记一份。
2. 每个 <code>Source</code> 提供实际动作事件推导出的 <code>damage_1s</code>、生命、防御、护盾、<code>recovery_30s</code> 与功能成本；涉及生命/防御的同一 Actor 必须使用一致、正数、固定的 <code>defense_k</code>。
3. <code>resolve()</code> 按服务器拥有的优先级和稳定来源 ID 排序，返回 <code>Applied</code>。连续属性可裁剪；不可分功能只能全部授予或不授予，不能给“0.4 次净化”。
4. 面板评分和实际事件必须读取同一个 <code>Applied</code> 快照。只把显示数字限制为 1 极，而伤害仍读取未裁剪原值，不符合本设计。
5. <code>EventLedger</code> 对真实事件按滑动窗口、唯一包身份与非递归规则记账。被拒绝事件不应扣血、治疗或提供功能收益；拒绝不能绕过为另一种伤害源。

<b><code>damage_1s</code></b><b> 是任意连续一秒的合法伤害总额上界，不是长期平均 DPS。</b> 不能把 <code>CombatScenarios225.TeamDPS</code> 或炮台含聚能平均 DPS 直接填进去。必须把聚能、技能爆发、多段、DOT 与多目标的实际时间位置一起计算；否则正常爆发会被错误拦截，或用过大的包上限放过超额输出。<code>recovery_30s</code> 同样须计入真实 30 秒治疗/护盾补充总额，不能只填写当前护盾容量。

示例仅演示内核接口，不代表游戏中的实际动作：

```py
from fractions import Fraction
from budget_reference import Source, resolve, score, EventLedger

applied = resolve([
    Source(
        source_id='player:base', priority=0,
        actor_id='player', defense_k=56,
        hp=600, defense=0,
        damage_1s=Fraction(40),
    )
])
ledger = EventLedger(applied)
approved = ledger.emit(
    source_id='player:base', action_id='attack:1',
    packet_id='hit:1', target_id='monster:1',
    kind='damage', amount=Fraction(40), server_ms=1000,
)
```

目标归属、阵营、无敌/安全状态、真实碰撞、可达射线、冷却、合法动作、目标当前生命、资源支付与存档幂等仍由工程权威层负责。内核不提供 Unreal Actor/蓝图绑定、网络复制、真实扣费或数据库事务。重建快照、跨场景与重连也不能因此清掉仍有效的冷却和去重状态。

## 八、数学验证与引擎验收的边界

本包检查覆盖行数和身份、公式/锚点、品质上限、预算守恒、概率归一化、资源成本、参考 TTK、回刷系数边界、精确大数裁剪及参考事件账本。

以下结果仍须在实际工程中取得证据后才能标记完成：原生弹体真实命中与扣血、所有技能实际段数/周期、宠物存活与追击空窗、DOT 边界与换装、多人所有权、掉落与培养事务幂等、旧存档迁移、跨模式隔离、断线重连、DS 负载、UI 读回和实际数值裁剪。现有炮台 1005“发射但未扣血”记录尤其不能被理论伤害表覆盖为已解决。

实施顺序应先完成字段与版本映射、单位及精确数表示，再接权威伤害/奖励路由，随后用固定样板核对原生事件和整队结果。偏差超过设计验收阈值时，先修正实际周期/命中模型和重复乘区，再调整怪物与经济；不要以修改页面显示数值代替真实结算。
